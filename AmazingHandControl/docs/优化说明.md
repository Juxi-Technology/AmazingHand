## 一、角度体系重新标定

### 1.1 角度限位：`0..110` → `-75..75`

原版按 `0° = 张开，110° = 握紧` 标定。实测本机行程落在 `-75..75`，因此重新标定。

**`data/config.yaml`**

| 配置项 | 原值 | 新值 |
|---|---|---|
| `servo_min` / `servo_max` | -40 / 110 | **-75 / 75** |
| `base_min` / `base_max` | 0 / 110 | **-75 / 75** |
| `side_min` / `side_max` | -40 / 40 | **-35 / 35** |
| `left_open` | `[32, -40]` | **`[32, -35]`** |
| `right_open` | `[-40, 32]` | **`[-35, 32]`** |
| `left_closed` / `right_closed` | `[110, 110]` | **`[75, 75]`** |
| `center_closed` | `[110, 110]` | **`[75, 75]`** |

**19 个 pose 全部按新尺度重标定**，例如 `open` 由 `[0]*8` 改为 `[-35]*8`，`close` 由 `[110]*8` 改为 `[75]*8`。

### 1.2 左右摆幅：`±40°` → `±35°`

左右滑块的归一化因子是 `u = |side_offset| / |side_min|`，只改限位不会改变实际张开幅度，必须**同时**改 `auto_extremes` 里的极值。两者一起改后：

| | 原（±40） | 现（±35） |
|---|---|---|
| 滑块范围 | −40 … +40 | −35 … +35 |
| 全开时左右摆到极限 | `(32, -40)`，开合差 **72°** | `(32, -35)`，开合差 **67°** |

### 1.3 统一到厂商基准

厂商 Arduino 演示程序（`Amazing_RHand_Demo.ino`）的换算为：

```c
float Step = 0.293; // 300°/1024
sc.RegWritePos(1, MiddlePos[0] + Pos_1 / Step, 0, Speed);
```

验证 rustypot 1.4.2 源码（`src/servo/feetech/scs0009.rs`）：

```rust
fn to_raw(value: f64) -> i16 {
    let a = (1024.0 * value / (300.0_f64.to_radians()) + 511.0) as i16;
    a.to_be()
}
```

**结论：两边的"度"是同一个刻度（0.29297°/step，300° 满量程，raw 0–1023），不存在比例错误。** 唯一的系统性差异是零点：

- rustypot 固定以 raw **511** 为中心
- 厂商固件用每轴标定值 `MiddlePos = {451, 571, 451, 571, 451, 571, 451, 571}`

两者相差 **±60 raw = ±17.6°**。这正是下面"Middle position"按钮要处理的问题。

## 二、全局按钮：改用舵机原始值精确控制

### 2.1 问题

原版 `open_all()` / `close_all()` 里写死了角度值：

```python
def open_all(self):
    for finger in self.fingers:
        finger.pos_var.set(0)      # 写死的 0
        finger.side_var.set(0)
        ...
def close_all(self):
    for finger in self.fingers:
        finger.pos_var.set(110)    # 写死的 110
```

这两个值来自**旧标定尺度**（0=张开、110=握紧）。重新标定到 `-35 / 75` 之后：

- `open_all` 设 0° → 换算后 raw = **511**，也就是**机械中位附近**，手指根本没张开
- `close_all` 设 110° → 被 `base_max = 75` 夹住，实际只到 75；而界面标签仍显示 110°

### 2.2 方案：新增原始值直发通道

角度通道要经过 `base/side` 插值模型，无法精确命中指定的 raw 值（后面第四节会详细说明）。因此为全局按钮新增一条**直接写舵机原始值**的通道。

**关键实现细节**：没有使用 rustypot 的 `sync_write_raw_goal_position`。查看宏生成源码发现，原始值接口直接 `values.to_le_bytes()` 上线，而转换接口的 `to_raw()` 先做了 `to_be()`：

```rust
fn to_raw(value: f64) -> i16 { let a = (... ) as i16; a.to_be() }
// sync_write_raw_*: values.iter().map(|v| v.to_le_bytes())   <- 没有 to_be
```

直接传 `451` 会发出 `0xC301`（即 49921）。因此改用 `sync_write_goal_position`（弧度），反推出**能精确落在目标 raw 上**的弧度值，取每个 raw 台阶的中点以规避截断误差。

### 2.3 三个按钮的原始值目标

新增 `data/config.yaml` → `raw_positions`（下标 0 → 舵机 ID 1）：

```yaml
raw_positions:
  open:   [260, 760, 260, 760, 260, 760, 260, 760]
  close:  [760, 260, 760, 260, 760, 260, 760, 260]
  middle: [451, 571, 451, 571, 451, 571, 451, 571]
```

| 按钮 | 行为 | 舵机 ID 1–8 原始位置 |
|---|---|---|
| ✋ Open All | 完全伸直 | 260, 760, 260, 760, 260, 760, 260, 760 |
| ✊ Close All | 完全握紧 | 760, 260, 760, 260, 760, 260, 760, 260 |
| ⊙ Center All | 左右回正（不改开合） | — |
| **Middle position** | **回到标定中位** | 451, 571, 451, 571, 451, 571, 451, 571 |

> ⚠️ `raw_positions` 是**每只手需要标定的值**。厂商对 `MiddlePos` 的原话是 "replace values by your calibration results"，换手或换舵机后需重新测量。

### 2.4 滑块同步的取舍

原始值绕过了 `base/side` 插值模型，没有精确对应值，因此按钮执行后滑块会被设到**最接近的整数**：

| 位置 | 滑块显示 |
|---|---|
| open | base = −73, side = 0 |
| close | base = +73, side = 0 |
| middle | base = −17, side = 0 |

代价是：之后再碰滑块，手会跳到差约 1 个原始单位（0.3°）的位置。这是刻意的取舍 —— 优先保证按钮命中的精确性。

## 三、新增 Middle position 按钮

在 `✋ Open All` / `✊ Close All` / `⊙ Center All` 右侧新增 **Middle position** 按钮，功能是回到**厂商标定的机械中位**（raw 451/571）。

**为什么需要它**：`open_all` 到 `close_all` 的中点并不是机械中位。厂商的中位是 `MiddlePos`，相对 raw 511 偏了 ±60 raw（±17.6°）。上电后需要有一个明确的、可复现的归零位置。

## 四、修复 GUI 与 CLI 动作不一致（核心问题）

### 4.1 现象

**同一个 pose，在 GUI 里点 `✓ Apply` 和用 CLI `--pose` 执行，手会做出不同的动作。**

### 4.2 根因

GUI 的 pose 下发走的是：

```
set_positions(p1, p2)  →  decompose 拆成 (base, side) 存进滑块
                       →  get_positions() 在 Auto 模式下用 compute_auto_positions() 重算
```

而 `compute_auto_positions` **不是** `decompose_servo_positions` 的精确逆运算（中心与极值都是经验值）。CLI 的 `apply_pose()` 则是直接下发。

实测 **19 个 pose 里有 12 个失真**，偏差最大到 32°：

| pose | 存储值 | GUI 实际发出 | 偏差 |
|---|---|---|---|
| `ring_close` | Ring `(75, -35)` | Ring `(43, -5)` | **32° / 30°** |
| `middle_close` | Middle `(75, -35)` | Middle `(43, -5)` | **32° / 30°** |
| `pointer_close` | Pointer `(75, -35)` | Pointer `(43, -5)` | **32° / 30°** |
| `thumb_close` | Thumb `(75, -35)` | Thumb `(43, -5)` | **32° / 30°** |
| `wave1` | `(-75, -3)` | `(-75, 9)` | 12° |
| `hifive` | Thumb `(-75, -3)` | Thumb `(-75, 9)` | 12° |
| `greeting` | Ring `(-18, -57)` | Ring `(-10, -68)` | 8° / 11° |
| `victory` | Middle `(-68, -9)` | Middle `(-75, 1)` | 7° / 10° |
| `paper` | Pointer `(-52, -22)` | Pointer `(-59, -16)` | 7° / 6° |
| `ok` | Pointer `(36, 46)` | Pointer `(38, 43)` | 2° / 3° |

**规律：凡是每根手指 `pos1 == pos2` 的对称 pose（`open` `close` `stone` `two` `scissors` `one` `three`）都能精确还原；凡是带左右张开的非对称 pose 都会走形。**

### 4.3 方案

新增 `_send_exact_positions()`，按 `SERVO_PAIRS` 顺序把角度直接发给 8 个舵机（等价于 CLI 的 `apply_pose`）。两个 pose 入口都改用它：

- Pose Management 的 `✓ Apply` 按钮
- `_apply_pose_from_config()` —— 序列播放器与 pose 列表

滑块仍由 `set_positions()` 更新（仅作显示），但**不再由滑块决定下发值**。

### 4.4 效果

修复后，**19 个 pose 全部满足 `存储值 == GUI 下发值 == CLI 下发值`**。

**副作用**：GUI 里这些手势的实际动作会变化（尤其是非对称姿势），这正是修复的预期效果。

## 五、Pose 数据修正

### 5.1 四个 `*_close` 姿势的写法错误

```yaml
# 修正前 —— 目标手指 (75, -35)
ring_close:    [75, -35, -35, -35, -35, -35, -35, -35]
middle_close:  [-35, -35, 75, -35, -35, -35, -35, -35]
pointer_close: [-35, -35, -35, -35, 75, -35, -35, -35]
thumb_close:   [-35, -35, -35, -35, -35, -35, 75, -35]
```

`(75, -35)` 拆解后是 `base = 20, side = -55`（超范围）→ 意思是**「只屈了 27%，同时往左甩到极限」**，并不是"闭合这根手指"。对照 `close` 和 `one` 里的正确写法应为 `(75, 75)`：

```yaml
# 修正后 —— 目标手指全闭 (75, 75)，其余保持张开 (-35, -35)
ring_close:    [75, 75, -35, -35, -35, -35, -35, -35]
middle_close:  [-35, -35, 75, 75, -35, -35, -35, -35]
pointer_close: [-35, -35, -35, -35, 75, 75, -35, -35]
thumb_close:   [-35, -35, -35, -35, -35, -35, 75, 75]
```

拆解验证：目标手指 `base = 75`（全闭）、`side = 0`（不左右偏）。

**影响**：使用这四个姿势的 `finger_roll` 序列，现在才是真正的"逐指卷曲"。

### 5.2 `greeting` / `paper` 的拇指

两者原本的拇指是 `(75, 75)`（完全闭合）。`paper`（布，摊开手掌）拇指闭合明显不对。

`greeting` 先改为 `(-75, -3)`（复用 `hifive` 的拇指外展值），但实机测试发现该步拇指要跑 **150°**，在 1.0s 内跑不完（详见 6.3）。最终：

```yaml
greeting: [-18, -57, -32, -32, -70, -7, -35, -35]   # 拇指改为 (-35, -35)，与 open 一致
paper:    [-19, -56, -34, -34, -52, -22, -75, -3]   # 保持拇指外展（平摊手掌）
```

两个 pose 的语义由此分开：`greeting` 是打招呼，拇指自然张开即可；`paper` 是平摊手掌，拇指外展。

## 六、序列播放器：时序与诊断修复

### 6.1 修复"未到位"误报（索引顺序 bug）

实机跑 `demo` 时出现三条误报：

```
⚠ Pose #42 'greeting': Servos did not reach target! Max error: 52°
```

**根因**：`_log_pose_completion` 把两组**顺序不同**的数组按下标直接相减。

- `monitor_servos()` 按**舵机 ID 顺序**写缓存：`latest_actual_positions[servo_id - 1] = ...`（下标 0 = ID1 = Pointer）
- 但传入的 `target_positions` 是 pose 数组，按**控件顺序** Ring / Middle / Pointer / Thumb（下标 0 = Ring = ID5）

等于拿 Ring 的目标去减 Pointer 的实测。

**证据**（用实测日志里的 `greeting` 数据复算）：

```
目标(控件序)    : [-18, -57, -32, -32, -70, -7, -75, -3]
实测(舵机序)    : [-68.85, -6.74, -33.69, -31.35, -18.46, -54.79, -74.12, -3.22]
按同序直接比    -> 最大误差 52°      <-- 修复前的算法
目标重排为舵机序: [-70, -7, -32, -32, -18, -57, -75, -3]
按舵机序比      -> 最大误差 2.21°    <-- 其实完美到位
```

**修复**：新增 `pose_to_servo_order()` / `servo_to_pose_order()` 两个转换函数，比对前对齐；打印时再转回同一顺序，使日志里 `target` 与 `current` 逐列可比。

### 6.2 修复完成检查的时机

原版在 pose 下发后**固定等 2000ms** 就做检查：

```python
self.root.after(2000, lambda ...: self._log_pose_completion(...))
```

但序列的延时只有 1.0s，于是检查时下一步已经在执行，读到的必然是下一步运动途中的位置：

```
25.388  Pose #40 'ok'      下发
26.782  Pose #41 'victory' 下发        <- 已经切走
27.742  Pose #40 'ok'      检查 -> 读的是走向 victory 途中的位置
```

**修复**：

1. `_apply_pose_from_config` 新增 `check_after` 参数。点 `✓ Apply` 单个 pose 时行为不变（2.0s + 等运动停止）；序列播放时传入**该步自己的延时**，检查落在步边界上（延时 − 100ms），且不再用"等运动停止"逻辑。
2. 新增**取代守卫**：`_log_pose_start` 记录 `current_pose_id`，检查时若已被更新的命令取代，则跳过到位判定，只打印 `current=<superseded>`。

### 6.3 序列延时调整

从实机日志反推出**真实有效速度**（speed 3 标称 172°/s）：

| pose | 行程 | 0.9s 时的误差 | 反推有效速度 |
|---|---|---|---|
| `ok` | 110° | 0.5° | 121.7°/s（71% 标称） |
| `victory` | 110° | 1.0° | 121.1°/s（70%） |
| `greeting` | 132° | 7.0° | 138.9°/s（81%） |

> 带载后实际速度约为标称的 **七成**。这是选择延时时的重要依据。

**`demo` 序列调整**：

```yaml
  demo:
    steps:
    - open:3,3,3,3,3,3,3,3|2.0s
    - close:6,6,6,6,6,6,6,6|2.0s
    - ok:3,3,3,3,3,3,3,3|1.0s
    - victory:3,3,3,3,3,3,3,3|1.0s
    - greeting:3,3,3,3,3,3,3,3|1.5s      # 由 1.0s 延长
    - close:6,6,6,6,6,6,6,6|2.0s         # 新增：末尾回归握紧
```

- `greeting` 延时 1.0s → **1.5s**：该步最大行程 132°（Ring 第 2 轴），1.0s 内跑不完
- **末尾新增一步 `close`**：让 `demo` 结束时手回到握紧状态，循环播放时衔接干净
- `demo` 总时长 7.0s → **9.5s**

### 6.4 `wave` 序列：左右摆幅限制到 ±30°

原 `wave_r` / `wave_l` 隐含的 `side` 达到 **±36**（超出 ±35 限位被裁到 35）。

按 `side = base − pos1`、`base = (pos1 + pos2) / 2` 反解得 `pos1 = base − side`、`pos2 = base + side`，保持 `base = −39` 不变、把 `side` 收到 ±30：

```yaml
wave_r: [-9, -69, -9, -69, -9, -69, -69, -9]     # 原 [-3, -75, -3, -75, -3, -75, -75, -3]
wave_l: [-69, -9, -69, -9, -69, -9, -9, -69]     # 原 [-75, -3, -75, -3, -75, -3, -3, -75]
```

验证：`wave_r` 的 side = `[-30, -30, -30, +30]`，`wave_l` 是它的逐指镜像。

**副作用（预期内）**：单次挥动的行程也从 40°/72° 降到 **34°/60°**，挥手幅度整体收窄，时序余量反而更宽。

## 七、Servo Feedback 新增原始位置行

在 `Position (°)` 正下方新增一行 **`Current (0-1023)`**，实时显示舵机原始位置。

```
1. Goal (°)
2. Position (°)
3. Current (0-1023)      <== 新增
4. Speed (°/s)
5. Torque (%)
6. Voltage (V)
7. Current (mA)
8. Temperature (°C)
9. Status
10. Moving
```

**实现取舍**：不做额外的串口读取，原始值从监控线程**已经读到**的当前位置换算，避免每个轮询周期串口往返翻倍。换算精度经全量验证：**2048 个组合（raw 0–1023 × 奇/偶轴）往返零误差**。

**用途**：可以直接对照厂商标定值核对 —— `open` 时看到 `260 / 760` 交替，`middle` 时是 `451 / 571`。

> 行名加了量程前缀以区别于已有的 `Current (mA)`（电流估算行）。

## 八、左右手支持

### 8.1 厂商的两套固件

厂商为左右手各提供一个 Arduino 演示程序，两者参数完全不同：

| 项目 | 右手 `Amazing_RHand_Demo` | 左手 `Amazing_LHand_Demo` |
|---|---|---|
| 舵机 ID | **1–8** | **11–18** |
| 手指 → ID | 食指 `1,2` / 中指 `3,4` / 无名指 `5,6` / 拇指 `7,8` | **无名指 `11,12` / 中指 `13,14` / 食指 `15,16` / 拇指 `17,18`** |
| 中位 `MiddlePos` | `[451, 571, 451, 571, …]` | `[571, 451, 571, 451, …]` |

调试教程原文：**「单个灵巧手共使用了 8 个舵机，右手 ID 需要设置为 1-8，左手 ID 需要设置为 11-18」**。

注意左手的编号顺序是**反的**（无名指在前）—— 和镜像的机械结构对应。

### 8.2 为什么不能只改 ID

ID 只是第一层。左右手之间还有两处物理差异，漏掉任何一处手势都会走形。

#### 差异一：安装偏移 35.16°

两边用的是**同一个手势值 + 各自的 `MiddlePos`**：

```c
// 右手
#define MiddlePos {451, 571, ...}
Move_Index(-35, 35)  →  ID1 = 451 + (-35)/0.293 = 331.5

// 左手
#define MiddlePos {571, 451, ...}
Move_Index(-35, 35)  →  ID15 = 571 + (-35)/0.293 = 451.5
```

同一个「张开」动作，左右手到达的 raw 值不同。换算到本程序的角度空间，两者相差 **120 raw = 35.16°**。

#### 差异二：同指双舵机互换

```c
// 右手 Victory                      // 左手 Victory
Move_Index (-15, 65);                Move_Index (-65, 15);
Move_Middle(-65, 15);                Move_Middle(-15, 65);
```

每根手指的 `(a, b) → (-b, -a)`，换算成姿势值就是**把每根手指的两个数对调**。

漏掉这一步，**张开方向会整个反过来** —— 症状是 V 字手势的两指并拢、该并拢的三指反而张开。

> 一个容易看错的点：`Perfect` 里食指/中指的值左右手**完全相同**（`(50,-50)`、`(0,0)`），只有拇指不同。所以这不是「食指中指互换」，而是每指独立的 `(-b,-a)` —— 对称的数对做这个变换等于不变。

### 8.3 实现

**两只手共用同一份 `hand_config.yaml`。** 文件里存的姿势始终是**右手序**，左手只在读取和写回时做转换，所以不需要维护两套姿势库。

转换集中在 `hand_logic.py`：

| 函数 | 作用 |
|---|---|
| `resolve_hand_config(app_config, hand)` | 把 `hands.<name>` 的覆盖项合并到顶层（右手）配置上 |
| `servo_pairs()` / `servo_ids()` | 该手各手指的 `(servo1_id, servo2_id)` / 全部舵机 ID（升序） |
| `hand_angle_offset()` / `hand_mirrors_pose()` | 读取该手的两个差异参数 |
| `adapt_pose_for_hand(positions, mirror)` | 对每根手指做 `(pos1, pos2)` 对调。**交换是自逆运算**，所以同一个函数既用于「应用时转换」也用于「保存时转回」 |

**接入的路径：**

- GUI：pose 应用（`✓ Apply` 与序列播放）、保存 pose
- CLI：`--pose` / `--sequence`

**三个全局按钮的原始值**是每只手各自配置的，不走这套转换（`raw_positions` 已写在 `hands.left` 里）。

### 8.4 使用方法

启动 GUI 时先选：

```
  AmazingHand — which hand?
    1 = right hand  (servo IDs 1-8)
    2 = left hand   (servo IDs 11-18)
  Enter 1 or 2 [1]:
  LEFT hand — servo IDs 11-18
    Ring (11, 12)  Middle (13, 14)  Pointer (15, 16)  Thumb (17, 18)
    middle position raw: [571, 451, 571, 451, 571, 451, 571, 451]
```

选完才弹出界面；直接回车用 `config.yaml` 里的 `hand` 值。跳过提问：

```bash
python amazing_hand_gui.py --hand left
python amazing_hand_cmd.py --pose victory --hand left
```

### 8.5 左手首次标定核对

`hands.left.raw_positions` 里只有 **middle 是厂商默认值**（`571, 451`），`open` / `close` 是从厂商演示程序推导的：

| 按钮 | 左手 raw | 来源 |
|---|---|---|
| Middle position | `571, 451, …` | 厂商默认值 |
| Open All | `380, 642, …` | 推导：右手 Open All 的同一手势，套到左手 `MiddlePos` |
| Close All | `880, 142, …` | 同上 |

**第一次接上左手时按这个顺序核对：**

1. 按 **Middle position**，看 Servo Feedback 的 `Current (0-1023)` 行是否读到 `571, 451, 571, 451, …`
2. 按 **Open All** / **Close All**，确认行程到位且不顶限位
3. 逐个试 `victory`（食指中指分开成 V）、`greeting`（三指并拢）、`ok`（拇指食指指尖相触）

哪一项不对：

| 现象 | 改哪里 |
|---|---|
| Middle position 读数不对 | `hands.left.raw_positions.middle` |
| 张开方向反了 | `hands.left.mirror_pose` 改成 `false` |
| 行程不够或过头 | `hands.left.raw_positions.open` / `close` |

### 8.6 如果左手被编号成 1-8

有些人会把左手的舵机重新编号成 1–8。那样只需改 `hands.left.servos`：

```yaml
hands:
  left:
    servos:
      # 按厂商左手顺序重编：无名指在前
      ring:    [1, 2]
      middle:  [3, 4]
      pointer: [5, 6]
      thumb:   [7, 8]
      all_ids: [1, 2, 3, 4, 5, 6, 7, 8]
```

> `angle_offset` 和 `mirror_pose` **不用改** —— 它们是机械安装的属性，与 ID 编号无关。偶数 ID 取反的规则也仍然成立，因为每对手指都保持「奇数在前」。

## 九、串口端口自动检测

### 9.1 问题

原版在 Windows 上把端口列表写死成 `COM1`–`COM20`：

```python
available_ports = [f'COM{i}' for i in range(1, 21)]
```

而实际板子可能落在任意端口号上（本机实测是 `COM243`）。结果是**下拉框里根本没有你的端口**，自动连接又去连配置里不存在的默认值，报「系统找不到指定的文件」。

### 9.2 方案

新增 `available_serial_ports()`，逐级回退：

1. `pyserial` 的 `list_ports.comports()`（装了就用，信息最全）
2. Windows 且无 pyserial 时，读注册表 `HARDWARE\DEVICEMAP\SERIALCOMM`（**纯标准库**，不引入依赖）
3. Linux/macOS 用 glob 扫 `/dev/ttyACM*`、`/dev/ttyUSB*`、`/dev/ttyAMA*`、`/dev/cu.usb*`
4. 都失败才退回原来的候选列表

端口按**自然顺序**排序，`COM2` 排在 `COM10` 前面。

### 9.3 配套调整

- 下拉框从 `readonly` 改为**可编辑** —— 检测不到时可以直接手打端口号
- 配置里的默认端口不存在时，**自动回退到检测到的第一个真实端口**，不再拿不存在的默认值去连
- **显式传 `--port` 时不会被自动回退覆盖**（用 `port_was_explicit` 标记区分）

## 十、配置项速查

### `data/config.yaml`

顶层（`servos` / `auto_extremes` / `raw_positions`）描述**右手**，也是缺省值；`hands.<名称>` 按 key 覆盖它们。

```yaml
hand: right           # 当前使用的手：right | left（GUI 启动时会问，--hand 可跳过）

limits:
  servo_min: -75      # 舵机角度绝对下限
  servo_max: 75       # 舵机角度绝对上限
  base_min: -75       # 开合滑块范围（-75 = 全开）
  base_max: 75        #                （ 75 = 全握）
  side_min: -35       # 左右滑块范围
  side_max: 35

auto_extremes:        # 左右极限处的舵机位置 —— 右手
  left_open:  [32, -35]
  right_open: [-35, 32]
  left_closed:  [75, 75]
  right_closed: [75, 75]

raw_positions:        # 全局按钮的原始值目标 —— 右手（下标 0 → 舵机 ID 1）
  open:   [260, 760, ...]
  close:  [760, 260, ...]
  middle: [451, 571, ...]

hands:
  left:               # 左手覆盖项，只需写与右手不同的部分
    servos:
      ring:    [11, 12]
      middle:  [13, 14]
      pointer: [15, 16]
      thumb:   [17, 18]
    raw_positions:    # 下标 0 → 舵机 ID 11
      open:   [380, 642, ...]
      close:  [880, 142, ...]
      middle: [571, 451, ...]
    angle_offset: -35.16   # 安装偏移（见 8.2）
    mirror_pose: true      # 同指双舵机互换（见 8.2）
```

`auto_extremes` 左右手**共用** —— 左右滑块在姿势空间里的行为一致，镜像手只是物理上朝相反方向张开。

### `data/hand_config.yaml`

pose 的 8 个值按 **Ring, Middle, Pointer, Thumb** 顺序排列（对应舵机对 `(5,6) (3,4) (1,2) (7,8)`），**不是**舵机 ID 顺序。

**这个文件左右手共用，存储的永远是右手序。** 左手在应用时做同指互换，保存时再换回来。

> ⚠️ `amazing_hand_cmd.py` 的 docstring 写作 "index 0→servo1 … 7→servo8"，**该注释是错的**，请勿照它修改。

## 十一、实机验证数据

### 到位精度（修复后）

| pose | 目标 | 实测 | 最大误差 |
|---|---|---|---|
| `open` | 全 −35 | −36.6 ~ −33.4 | ≤1.6° |
| `close` | 全 75 | 74.7 ~ 75.3 | ≤0.3° |
| `ok` | — | — | 0.5° |
| `victory` | — | — | 1.0° |
| `greeting` | — | — | 2.2° |

### 换算校验

```
raw -> degrees -> raw 往返 2048 个组合，零误差
open    原始值 [260, 760] -> 反算 [260, 760]
middle  原始值 [451, 571] -> 反算 [451, 571]
close   原始值 [760, 260] -> 反算 [760, 260]
```

### 已知残留问题

- **`demo` 里 `ok` 和 `victory` 两步的时序余量接近零**（按实测速度算 +0.01s）。目前靠"误差 < 5° 容差"通过。电池电压下降、温度变化或手指变紧都可能把它们推过阈值。建议把这俩的延时从 1.0s 提到 1.2s。
- **`scissors` 与 `two` 逐字节相同**、**`stone` 与 `close` 逐字节相同**。语义上说得通（剪刀手 = 比二，石头 = 拳），属字面重复，未清理。
- **滑块与原始值之间仍有约 0.3° 的表示误差**（见 2.4）。
- **`config.yaml` 与 `hand_logic.py` 的 `default_config` 已不同步**。后者仍是原版值（`servo_min: -40` 等），只在 `config.yaml` 缺失时用作兜底。测试 `test_hand_logic.py::TestAngleLimits::test_defaults` 断言的正是这套旧默认值。

### 术语对照

| 界面用语 | 含义 |
|---|---|
| **Auto 模式** | 用「开合 base + 左右 side」两个滑块间接控制一根手指的两个舵机 |
| **Raw 模式** | 直接控制一根手指的两个舵机角度 |
| **base** | 开合程度，`(pos1 + pos2) / 2` |
| **side** | 左右偏移，`base − pos1` |
| **原始值 / raw** | 舵机内部位置单位，0–1023 对应 300° 行程，中位 511 |
| **MiddlePos** | 厂商固件里的每舵机中位标定值，左右手不同（见 8.1） |
| **angle_offset** | 左右手的安装偏移，35.16°（见 8.2） |
| **mirror_pose** | 左手特有的同指双舵机互换（见 8.2） |
